## Как приложение подключается к базе данных?

Перед тем как говорить про транзакции, поговорим как вообще подключаются к базе данных.

Приложение не “магически” отправляет SQL-запросы в базу. Оно подключается к PostgreSQL через соединение.

Соединение с PostgreSQL — это обычное сетевое TCP-соединение между приложением и сервером PostgreSQL. 


```text
backend-приложение
    |
    | TCP-соединение
    |
PostgreSQL server, port 5432
```

Соединение может быть как синхронным, так и асинхронным. Важно уточнить: само соединение с PostgreSQL в обоих случаях обычно остаётся обычным сетевым соединением. Разница между синхронной и асинхронной работой не в том, что база подключается “по-другому”, а в том, как приложение ждёт ответ от базы, хоть и для асинхронного подключения нужно подключаться по отдельному адресу к базе данных.

То есть асинхронность — это в первую очередь про поведение приложения, а не про какую-то принципиально другую работу внутри PostgreSQL.

Ещё важный момент: одно соединение с базой не превращается в бесконечный поток запросов к базе. Если нужно реально обслуживать много запросов одновременно, обычно используют несколько соединений в пуле.

Внутри этого соединения данные передаются через собственный протокол общения PostgreSQL  между клиентом и сервером. 

То есть когда мы в коде пишем что-то вроде:

```python
cursor.execute("SELECT * FROM users")
```

на самом деле драйвер в фреймворке нашего кода берёт SQL-строку, упаковывает её в сообщения PostgreSQL-протокола и отправляет по открытому соединению в базу.

==**Теперь важный момент.**==

Открывать новое соединение к базе на каждый запрос — дорого. Нужно установить сетевое соединение, пройти аутентификацию, создать сессию на стороне PostgreSQL. В свою очередь сессия на стороне PostgreSQL — это состояние, которое PostgreSQL создаёт и хранит для конкретного подключенного клиента.

Когда приложение подключается к PostgreSQL, сервер не просто получает “одно сообщение с SQL”. Он создаёт отдельный контекст работы для этого клиента.

В этом контексте PostgreSQL хранит, например:

```
- кто подключился;
- к какой базе подключился;
- какие настройки действуют для этого подключения;
- какая сейчас открыта транзакция, если она есть;
- какие временные таблицы созданы в этой сессии;
- какой запрос сейчас выполняется.
```

Упрощённо можно думать так:

```
соединение — это канал связи между приложением и PostgreSQL;

сессия — это состояние этого клиента внутри PostgreSQL,
которое живёт, пока соединение открыто;

для каждого соединения есть одна своя сессия. можно это представлять как отдельные телефонный звонки одному оператору колл-центра, который должен ответить всем клиентам.
```

Поэтому создание нового соединения дорогое: PostgreSQL должен принять сетевое подключение, выполнить аутентификацию, создать серверный контекст для клиента и подготовить всё, чтобы этот клиент мог выполнять SQL-запросы.

Поэтому нормальные backend-приложения используют пул соединений.

Пул соединений — это набор заранее открытых соединений к базе данных:

```text
connection pool:

connection_1 -> PostgreSQL
connection_2 -> PostgreSQL
connection_3 -> PostgreSQL
connection_4 -> PostgreSQL
connection_5 -> PostgreSQL
```

Когда в приложение приходит какой-то запрос, приложение берёт свободное соединение из пула, выполняет SQL-запросы, а потом возвращает соединение обратно в пул, а не создает и удаляет их постоянно.

Пример:

```text
запрос от пользователя Niko на изменение данных в базе
    |
приложение берёт connection_1 из пула
    |
выполняет SQL-запросы
    |
делает COMMIT или ROLLBACK (поговорим что это такое позже)
    |
возвращает connection_1 обратно в пул
```

Если одновременно пришло несколько запросов на получение данных в наше приложение, то они могут взять разные соединения из пула:

```text
запрос 1 -> connection_1 -> transaction_1
запрос 2 -> connection_3 -> transaction_2
запрос 3 -> connection_5 -> transaction_3
```

На этом этапе важно понять только одну вещь: разные запросы на взаимодействие с базой в наше приложение могут одновременно использовать разные соединения к базе.

Например:

```
HTTP-запрос 1:
получить пользователя по id

HTTP-запрос 2:
получить список заказов

HTTP-запрос 3:
получить остатки товаров
```

Приложение может раздать им разные соединения из пула:

```sql
запрос 1 -> connection_1 -> SELECT * FROM users WHERE id = 10;

запрос 2 -> connection_3 -> SELECT * FROM orders WHERE user_id = 10;

запрос 3 -> connection_5 -> SELECT * FROM products WHERE stock > 0;
```

Для разработчика это выглядит как обычный код:

```
user = db.fetch_one("SELECT * FROM users WHERE id = 10")
orders = db.fetch_all("SELECT * FROM orders WHERE user_id = 10")
products = db.fetch_all("SELECT * FROM products WHERE stock > 0")
```

Но внутри приложения эти запросы могут выполняться через разные соединения к PostgreSQL.

То есть пул соединений позволяет приложению не создавать новое подключение к базе каждый раз, а переиспользовать уже открытые соединения. ==Для разработчика важно заранее знать нагрузку на свое приложение, какие запросы отправляются в базу данных, чтобы рассчитать сколько одновременных постоянных пул соединений нужно держать в приложении с базой данных.==

## Главная идея:

```
1. без пула:
каждый раз заново подключаемся к базе

2. с пулом:
берём уже открытое соединение,
выполняем запрос,
возвращаем соединение обратно

3. поэтому нужно опытным путем научиться подбирать количество постоянных соединений
```
