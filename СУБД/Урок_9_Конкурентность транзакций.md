## 2. Основная проблема

Когда транзакция одна, всё относительно просто.

Она открылась, выполнила команды и завершилась:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 300
WHERE id = 1;

COMMIT;
```

Но в реальном приложении транзакция почти никогда не одна.

Допустим, два пользователя одновременно делают действия, которые затрагивают один и тот же баланс.

Начальное состояние:

```text
accounts

id | name | balance
---|------|--------
1  | Niko | 1500
```

Первая транзакция хочет списать `300`.

Вторая транзакция хочет списать `500`.

Если всё выполнить последовательно, правильный итог очевиден:

```text
1500 - 300 - 500 = 700
```

Но если две транзакции одновременно прочитают старое значение `1500`, каждая посчитает свой новый баланс и потом обе запишут результат, одна операция может затереть другую.

Главная проблема конкурентности:

> несколько транзакций могут одновременно читать и менять одни и те же данные, и из-за этого итоговое состояние базы может получиться логически неправильным.

## 3. Какие проблемы бывают при параллельных транзакциях

Сначала разберём не термины, а сами проблемы человеческим языком.

### 3.1. Прочитали временную херню

Одна транзакция изменила данные, но ещё не сделала `COMMIT`.

Вторая транзакция взяла и прочитала эти данные.

Потом первая транзакция сделала `ROLLBACK`.

Получается, вторая транзакция увидела данные, которых в базе по факту никогда не было в зафиксированном состоянии.

Пример:

```text
Было:

Niko = 1500
```

Первая транзакция:

```sql
BEGIN;

UPDATE accounts
SET balance = 0
WHERE id = 1;

-- COMMIT ещё не было
```

Вторая транзакция читает:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

И видит:

```text
Niko = 0
```

Потом первая транзакция делает:

```sql
ROLLBACK;
```

И база возвращается к состоянию:

```text
Niko = 1500
```

То есть значение `0` никогда не стало настоящей зафиксированной реальностью. Но вторая транзакция уже могла использовать его для какой-нибудь логики.

Термин: **dirty read**, или **грязное чтение**.

В PostgreSQL в нормальной работе грязного чтения нет. Даже если выставить уровень `READ UNCOMMITTED`, PostgreSQL фактически не даёт читать незакоммиченные изменения других транзакций.

---

### 3.2. Два раза прочитали одну строку и получили разные значения

Транзакция читает строку.

Потом другая транзакция меняет эту строку и делает `COMMIT`.

Первая транзакция снова читает эту же строку и видит уже другое значение.

Пример:

```text
Было:

Niko = 1500
```

Первая транзакция:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;

-- получила 1500
```

Вторая транзакция:

```sql
BEGIN;

UPDATE accounts
SET balance = 1000
WHERE id = 1;

COMMIT;
```

Первая транзакция снова делает:

```sql
SELECT balance
FROM accounts
WHERE id = 1;

-- получила 1000
```

Внутри одной транзакции один и тот же запрос к одной и той же строке дал разные результаты.

Это может быть нормально для некоторых сценариев, но может быть опасно, если приложение ожидало стабильную картину данных.

Термин: **non-repeatable read**, или **неповторяющееся чтение**.

---

### 3.3. Список строк внезапно изменился

Иногда мы читаем не одну строку, а набор строк по условию.

Например:

```sql
SELECT *
FROM orders
WHERE user_id = 10;
```

Транзакция первый раз выполнила запрос и получила 2 заказа.

Потом другая транзакция добавила ещё один заказ этому пользователю и сделала `COMMIT`.

Первая транзакция повторяет тот же запрос и получает уже 3 заказа.

Пример:

```text
Первое чтение:

orders for user_id = 10

id | amount
---|-------
1  | 500
2  | 700
```

Параллельно другая транзакция:

```sql
BEGIN;

INSERT INTO orders(user_id, amount)
VALUES (10, 1000);

COMMIT;
```

Повторное чтение:

```text
orders for user_id = 10

id | amount
---|-------
1  | 500
2  | 700
3  | 1000
```

Новая строка как будто появилась “из воздуха” между двумя одинаковыми запросами.

Термин: **phantom read**, или **фантомное чтение**.

Отличие от прошлой проблемы:

```text
non-repeatable read:
изменилась уже существующая строка

phantom read:
изменился набор строк, подходящих под условие
```

---

### 3.4. Одна запись затёрла другую

Это одна из самых понятных и самых неприятных проблем.

Две транзакции читают одно и то же значение.

Обе на его основе считают новое значение.

Потом обе записывают результат.

В итоге запись одной транзакции затирает результат другой.

Начальное состояние:

```text
Niko = 1500
```

Первая транзакция:

```text
прочитала 1500
посчитала 1500 - 300 = 1200
```

Вторая транзакция:

```text
прочитала 1500
посчитала 1500 - 500 = 1000
```

Дальше:

```text
первая транзакция записала 1200
вторая транзакция записала 1000
```

Итог:

```text
Niko = 1000
```

Но правильный итог должен быть:

```text
Niko = 700
```

Потому что нужно было применить оба списания:

```text
1500 - 300 - 500 = 700
```

Получается, списание на `300` просто потерялось.

Термин: **lost update**, или **потерянное обновление**.

Это особенно часто возникает, когда разработчик делает логику так:

```text
1. SELECT balance
2. посчитать новое значение в коде приложения
3. UPDATE balance = новое_значение
```

То есть ошибка часто не в самой базе, а в том, что приложение слишком рано забрало данные из базы, посчитало что-то у себя в коде и потом записало старый расчёт обратно.

---

### 3.5. Каждая транзакция по отдельности права, но вместе они ломают правило

Это самая мерзкая проблема, потому что она не всегда выглядит очевидно.

Есть правило:

```text
в больнице всегда должен быть хотя бы один дежурный врач
```

Таблица:

```text
doctors

id | name | on_call
---|------|--------
1  | Ivan | true
2  | Petr | true
```

Первая транзакция хочет снять Ивана с дежурства.

Вторая транзакция хочет снять Петра с дежурства.

Первая транзакция проверяет:

```sql
SELECT COUNT(*)
FROM doctors
WHERE on_call = true;
```

Видит:

```text
2 дежурных врача
```

Думает:

```text
если я сниму Ивана, всё равно останется Пётр
```

Вторая транзакция одновременно делает такую же проверку.

Тоже видит:

```text
2 дежурных врача
```

Тоже думает:

```text
если я сниму Петра, всё равно останется Иван
```

Дальше первая транзакция делает:

```sql
UPDATE doctors
SET on_call = false
WHERE id = 1;
```

Вторая транзакция делает:

```sql
UPDATE doctors
SET on_call = false
WHERE id = 2;
```

Обе коммитятся.

Итог:

```text
doctors

id | name | on_call
---|------|--------
1  | Ivan | false
2  | Petr | false
```

Дежурных врачей осталось ноль.

Каждая транзакция по отдельности рассуждала нормально. Но вместе они сломали бизнес-правило.

Термин: **write skew**.

Это не совсем потерянное обновление, потому что транзакции не затирали одну и ту же строку. Они обновляли разные строки. Проблема в том, что обе принимали решение на основе общего условия.

## 4. Что PostgreSQL делает, чтобы база не превратилась в кашу

PostgreSQL использует механизм MVCC.

MVCC расшифровывается как Multi-Version Concurrency Control.

По-человечески:

> PostgreSQL может хранить несколько версий одной и той же строки и решать, какую версию показывать конкретной транзакции.

Допустим, есть строка:

```text
id = 1, name = Niko, balance = 1500
```

Транзакция делает:

```sql
UPDATE accounts
SET balance = 1200
WHERE id = 1;
```

Очень упрощённо это можно представить так:

```text
старая версия строки:

id = 1, name = Niko, balance = 1500

новая версия строки:

id = 1, name = Niko, balance = 1200
```

PostgreSQL не обязан сразу уничтожать старую версию строки, потому что она может быть ещё нужна другим транзакциям.

Например, одна транзакция началась раньше и по своим правилам видимости ещё должна видеть старый баланс `1500`.

А другая транзакция, которая началась позже, уже может видеть новый баланс `1200`.

То есть важная мысль:

> в PostgreSQL разные транзакции могут одновременно видеть разные версии одной и той же логической строки.

Это звучит странно, но именно это позволяет PostgreSQL не блокировать всё подряд.

Если одна транзакция читает данные, а другая транзакция их меняет, PostgreSQL во многих случаях не заставляет чтение и запись всегда ждать друг друга. Вместо этого он показывает читающей транзакции ту версию строки, которую ей разрешено видеть.

Очень грубо:

```text
транзакция A читает старую версию строки
транзакция B создаёт новую версию строки
```

Из-за этого PostgreSQL может нормально выдерживать параллельную работу большого количества транзакций.

Но MVCC не решает вообще все проблемы автоматически. Он решает часть проблем, а для остальных нужны уровни изоляции, блокировки, ограничения и правильный код приложения.

## 5. Что такое snapshot и зачем он нужен

Snapshot нужен для ответа на главный вопрос:

> какую версию строки должна увидеть конкретная транзакция?

Если в базе есть несколько версий строки, PostgreSQL должен выбрать одну из них.

Например:

```text
версия 1:
Niko = 1500

версия 2:
Niko = 1200

версия 3:
Niko = 1000
```

Когда транзакция делает:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

PostgreSQL должен понять:

```text
какую версию показать этой транзакции?
1500?
1200?
1000?
```

Вот для этого и нужен snapshot.

Snapshot — это не физическая копия всей базы данных.

PostgreSQL не делает копию всех таблиц при каждом `BEGIN`. Это было бы слишком дорого.

Snapshot — это набор правил видимости.

То есть PostgreSQL примерно запоминает:

```text
какие транзакции уже завершились на момент snapshot;
какие транзакции ещё были активны;
какие изменения уже можно считать видимыми;
какие изменения пока показывать нельзя.
```

Простая метафора:

> snapshot — это очки, через которые транзакция смотрит на базу данных.

База может уже измениться. Другие транзакции могут уже сделать `COMMIT`. Но конкретная транзакция через свой snapshot может продолжать видеть старую картину мира.

Зачем это нужно?

Чтобы транзакция не сходила с ума от того, что база меняется прямо у неё под ногами.

Например, если мы строим отчёт, считаем сумму денег, проверяем сложное условие или читаем несколько связанных таблиц, нам часто нужно видеть данные согласованно, а не кусками из разных моментов времени.

Без snapshot может получиться так:

```text
счёт A прочитали до перевода
счёт B прочитали после перевода
итоговая сумма получилась такая, какой в реальности никогда не было
```

Snapshot помогает транзакции смотреть на данные как на согласованную картину на определённый момент времени.

## 6. Уровни изоляции в PostgreSQL

Теории здесь нужно немного. Главное — понять смысл.

Уровень изоляции отвечает на вопрос:

> насколько сильно моя транзакция изолирована от изменений других транзакций?

В PostgreSQL на практике важнее всего понимать три уровня:

```text
Read Committed
Repeatable Read
Serializable
```

### Read Committed

Это уровень по умолчанию в PostgreSQL.

Главная идея:

> каждый отдельный SQL-запрос видит только те данные, которые были закоммичены до начала этого конкретного SQL-запроса.

Важно:

```text
не до начала всей транзакции,
а до начала конкретного запроса
```

Пример:

```sql
BEGIN;

SELECT balance FROM accounts WHERE id = 1;
-- увидели 1500

-- в это время другая транзакция поменяла balance на 1000 и сделала COMMIT

SELECT balance FROM accounts WHERE id = 1;
-- можем увидеть уже 1000

COMMIT;
```

То есть на `Read Committed` два `SELECT` внутри одной транзакции могут увидеть разные данные.

Это нормально для этого уровня изоляции.

---

### Repeatable Read

Главная идея:

> транзакция видит snapshot базы на момент старта транзакции.

Если транзакция два раза прочитала одну и ту же строку, она увидит одно и то же значение, даже если другая транзакция уже изменила эту строку и сделала `COMMIT`.

Пример:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance FROM accounts WHERE id = 1;
-- увидели 1500

-- другая транзакция поменяла balance на 1000 и сделала COMMIT

SELECT balance FROM accounts WHERE id = 1;
-- всё ещё видим 1500

COMMIT;
```

То есть мир для транзакции как будто заморозился на момент её старта.

---

### Serializable

Главная идея:

> результат должен быть таким, как будто транзакции выполнились не параллельно, а строго по очереди.

PostgreSQL не обязательно реально ставит все транзакции в одну очередь.

Он может выполнять их параллельно.

Но если PostgreSQL видит, что параллельное выполнение может привести к некорректному результату, он может откатить одну из транзакций с ошибкой сериализации.

То есть на `Serializable` нормальная ситуация:

```text
одна транзакция успешно закоммитилась;
вторая получила ошибку;
приложение должно повторить вторую транзакцию.
```

Это важный момент для разработчиков.

`Serializable` — это не магия, которая всегда молча делает всё правильно. Иногда правильное поведение PostgreSQL — сказать приложению:

```text
я не могу безопасно закоммитить эту транзакцию, повтори её заново
```

## 7. Практика: что делать разработчику

Этот раздел черновой. Его потом можно перестроить и сделать главным практическим блоком урока.

### 7.1. Не делать “прочитал — посчитал в коде — записал обратно” без защиты

Плохой вариант:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;

-- в приложении:
-- new_balance = balance - 300

UPDATE accounts
SET balance = 1200
WHERE id = 1;

COMMIT;
```

Почему плохо?

Потому что между `SELECT` и `UPDATE` другая транзакция может изменить этот же баланс.

То есть приложение могло прочитать уже устаревшее значение, посчитать на его основе новый баланс и записать неправильный результат.

Лучше, если операция простая, делать изменение атомарно прямо в базе:

```sql
UPDATE accounts
SET balance = balance - 300
WHERE id = 1;
```

Так PostgreSQL сам выполнит изменение текущего значения.

---

### 7.2. Проверку условия лучше зашивать прямо в UPDATE

Например, нельзя списывать деньги, если баланса недостаточно.

Плохой вариант:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;

-- в приложении:
-- if balance >= 300:
--     списываем деньги

UPDATE accounts
SET balance = balance - 300
WHERE id = 1;

COMMIT;
```

Проблема та же: между чтением и обновлением баланс мог измениться.

Лучше:

```sql
UPDATE accounts
SET balance = balance - 300
WHERE id = 1
  AND balance >= 300;
```

После этого приложение проверяет, сколько строк обновилось.

Если обновилась одна строка:

```text
деньги успешно списались
```

Если обновилось ноль строк:

```text
денег не хватило или аккаунт не найден
```

Это хороший стиль, потому что проверка и изменение происходят одной SQL-командой.

---

### 7.3. Если нужно сначала прочитать строку, потом принять решение и изменить — используй FOR UPDATE

Иногда нельзя всё засунуть в один `UPDATE`.

Например, нужно прочитать строку, выполнить какую-то бизнес-логику, проверить статус, потом изменить данные.

Тогда можно заблокировать строку:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

-- здесь приложение принимает решение,
-- но строка уже заблокирована от конкурентного изменения

UPDATE accounts
SET balance = balance - 300
WHERE id = 1;

COMMIT;
```

`FOR UPDATE` говорит PostgreSQL:

```text
я собираюсь менять эти строки;
не дай другим транзакциям параллельно изменить их до завершения моей транзакции
```

Если другая транзакция тоже попробует изменить эту строку, она будет ждать.

Это не нужно пихать везде подряд. Но если у тебя есть схема:

```text
SELECT -> бизнес-решение -> UPDATE
```

и данные могут параллельно менять другие транзакции, то нужно думать о блокировке.

---

### 7.4. Для сложных бизнес-правил одной блокировки строки может быть мало

Пример с врачами:

```text
всегда должен быть хотя бы один дежурный врач
```

Проблема в том, что две транзакции могут менять разные строки, но ломать одно общее правило.

```text
T1 меняет строку Ivan
T2 меняет строку Petr
```

Они не конфликтуют по одной конкретной строке, но конфликтуют по смыслу бизнес-правила.

Тут варианты решения зависят от задачи:

```text
1. поднять уровень изоляции до SERIALIZABLE;
2. использовать явные блокировки;
3. использовать advisory lock;
4. выразить правило через constraint или индекс, если это возможно;
5. пересмотреть модель данных, чтобы инвариант контролировался проще.
```

Главная мысль:

> если бизнес-правило зависит не от одной строки, а от набора строк, обычный UPDATE одной строки может не защитить от всех проблем конкурентности.

---

### 7.5. На Serializable нужно уметь повторять транзакцию

Если используется уровень изоляции `Serializable`, приложение должно быть готово к ошибке сериализации.

Псевдокод:

```python
for attempt in range(3):
    try:
        begin_transaction(isolation_level="SERIALIZABLE")

        do_business_logic()

        commit()
        break

    except SerializationError:
        rollback()

        if attempt == 2:
            raise

        continue
```

То есть retry — это не костыль, а нормальная часть работы с конкурентными транзакциями.

## 8. Что разработчик должен вынести из урока

Главное не в том, чтобы зазубрить названия всех аномалий.

Главное — понять, что база данных живёт в параллельном мире.

В один и тот же момент разные соединения могут выполнять разные транзакции:

```text
одна транзакция читает данные;
другая транзакция меняет эти же данные;
третья транзакция вставляет новые строки;
четвёртая транзакция считает отчёт;
пятая транзакция проверяет бизнес-правило.
```

Из-за этого код, который выглядит нормально при одном пользователе, может сломаться при двух одновременных пользователях.

Разработчик должен помнить:

```text
1. Транзакция живёт внутри конкретного соединения.

2. Если начал транзакцию, её нужно закончить:
   COMMIT или ROLLBACK.

3. Не надо бездумно делать:
   SELECT -> посчитал в коде -> UPDATE.
   Между SELECT и UPDATE данные могли измениться.

4. Простые изменения лучше делать атомарно:
   UPDATE table
   SET value = value + ...
   WHERE ...

5. Проверки по возможности нужно писать прямо в UPDATE:
   UPDATE accounts
   SET balance = balance - 300
   WHERE id = 1 AND balance >= 300;

6. Если нужно сначала прочитать строку, а потом изменить,
   нужно подумать про SELECT ... FOR UPDATE.

7. Если бизнес-правило зависит от нескольких строк,
   нужно думать про Serializable, явные блокировки,
   advisory lock, constraints или другую модель данных.

8. Если используется Serializable,
   приложение должно уметь повторять транзакцию после ошибки сериализации.

9. Уровень изоляции — это не академическая херня,
   а настройка того, насколько сильно транзакция защищена
   от параллельных изменений других транзакций.

10. PostgreSQL помогает через MVCC, snapshot, блокировки
    и уровни изоляции, но он не отменяет необходимости
    нормально проектировать конкурентный код.
```

Короткая финальная мысль:

> Когда транзакция одна, главная задача — выполнить все команды целиком или откатить их.  
> Когда транзакций много, главная задача — не дать им одновременно прочитать и записать данные так, чтобы база пришла к логически неправильному состоянию.  
> Для этого в PostgreSQL есть MVCC, snapshot, блокировки и уровни изоляции. Но разработчик всё равно обязан понимать, где его код может сломаться при параллельном выполнении.
