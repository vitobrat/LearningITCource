## Как возникает проблема конкурентности паралелльных транзакций?

Когда транзакция одна, то всё просто: она открылась, выполнила команды и завершилась себе спокойно, не спеша. Но в реальном приложении отправляются дохуя транзакций и возможно даже несколькими приложениями или микросервисами.

### Пример
Допустим, два пользователя одновременно делают действия, которые затрагивают один и тот же баланс.

Начальное состояние:

```text

id | name | balance
---|------|--------
1  | Niko | 1500
```

Первой транзакцией нужно списать `300` тугриков.

Второй транзакцией нужно списать `500` тугриков.

Если всё выполнить последовательно, правильный итог очевиден:

```text
1500 - 300 - 500 = 700
```

Но нашу базу данных дрочат сотни транзакций каждую секунду и обрабатывать все по очереди ебанешься как долго, поэтому нужно оптимизироваться и обрабатывать запросы паралелльно. 
Но если в нашем примере 2 транзакции одновременно прочитают старое значение `1500`, то каждая посчитает свой новый баланс и потом обе запишут результат и одна операция  затрёт другую.

Отсюда вырисовывается главная проблема конкурентности:

> несколько транзакций могут одновременно читать и менять одни и те же данные, и из-за этого итоговое состояние базы может получиться неправильным, т.е. не так как мы ожидали и хотели бы

---

## Какие проблемы бывают при параллельных транзакциях?

### 1. Прочитали временную херню

Представим случай: одна транзакция изменила данные, но ещё не сделала `COMMIT`.

Вторая транзакция взяла и прочитала эти данные.

Потом первая транзакция сделала `ROLLBACK`.

Получается, вторая транзакция увидела данные, которых в базе по факту никогда не было в зафиксированном состоянии.

Пример:

```text
Было:

Niko = 1500
```

Первая транзакция:

```sql
BEGIN;

UPDATE accounts
SET balance = 0
WHERE id = 1;

-- COMMIT ещё не было
```

Вторая транзакция читает:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

И видит:

```text
Niko = 0
```

Потом первая транзакция делает:

```sql
ROLLBACK;
```

И база возвращается к состоянию:

```text
Niko = 1500
```

То есть значение `0` никогда не стало настоящей зафиксированной реальностью. Но вторая транзакция уже могла использовать его для какой-нибудь логики.

У этого есть термин: **dirty read**, или **грязное чтение**.

В PostgreSQL в нормальной работе грязного чтения нет. PostgreSQL фактически не даёт читать незакоммиченные изменения других транзакций.

### 2. Два раза прочитали одну строку и получили разные значения

Транзакция читает строку.

Потом другая транзакция меняет эту строку и делает `COMMIT`.

Первая транзакция снова читает эту же строку и видит уже другое значение.

Пример:

```text
Было:

Niko = 1500
```

Первая транзакция:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1;

-- получила 1500
```

Вторая транзакция:

```sql
BEGIN;

UPDATE accounts
SET balance = 1000
WHERE id = 1;

COMMIT;
```

Первая транзакция снова делает:

```sql
SELECT balance
FROM accounts
WHERE id = 1;

-- получила 1000
```

Внутри одной транзакции один и тот же запрос к одной и той же строке дал разные результаты.

Это может быть нормально для некоторых сценариев, но может быть опасно, если приложение ожидало стабильную картину данных.

У этого есть термин: **non-repeatable read**, или **неповторяющееся чтение**.

Чтобы не получить такую проблему в PostgreSQL, есть два простых подхода.

Первый вариант — не читать одни и те же данные несколько раз внутри одной транзакции, если в этом нет необходимости. Прочитали значение один раз — используем его дальше в коде.

Второй вариант — если внутри транзакции нужно стабильно видеть одну и ту же картину данных, нужно запускать транзакцию на уровне изоляции `REPEATABLE READ` (пдробно все уровни изоляции рассмотрим позже):

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance
FROM accounts
WHERE id = 1;

-- даже если другая транзакция изменит balance и сделает COMMIT,
-- внутри этой транзакции мы всё равно будем видеть старое значение

SELECT balance
FROM accounts
WHERE id = 1;

COMMIT;
```

Главная мысль:

> Если хочешь, чтобы повторное чтение внутри транзакции возвращало те же данные, используй ==`REPEATABLE READ`==.

### 3. Список строк внезапно изменился

Иногда мы читаем не одну строку, а набор строк по условию.

Например:

```sql
SELECT *
FROM orders
WHERE user_id = 10;
```

Транзакция первый раз выполнила запрос и получила 2 заказа.

Потом другая транзакция добавила ещё один заказ этому пользователю и сделала `COMMIT`.

Первая транзакция повторяет тот же запрос и получает уже 3 заказа.

Пример:

```text
Первое чтение:

id | amount
---|-------
1  | 500
2  | 700
```

Параллельно другая транзакция:

```sql
BEGIN;

INSERT INTO orders(user_id, amount)
VALUES (10, 1000);

COMMIT;
```

Повторное чтение:

```text

id | amount
---|-------
1  | 500
2  | 700
3  | 1000
```

Новая строка как будто появилась прямо на лету между двумя одинаковыми запросами.

У этого есть термин: **phantom read**, или **фантомное чтение**.

Отличие от прошлой проблемы:

```text
non-repeatable read:
изменилась уже существующая строка

phantom read:
изменилось количество строк
```
Практический вывод здесь такой же, как и в прошлой проблеме: сначала нужно понять, нужна ли нам стабильная картина данных внутри одной транзакции вообще.

Если это обычное чтение списка для отображения пользователю, то изменение количества строк между запросами может быть нормальным поведением.

Но если внутри одной транзакции нам важно несколько раз видеть один и тот же набор строк, можно использовать `REPEATABLE READ`, как в прошлом примере или для более строгой изоляции данных — `SERIALIZABLE`, который мы рассмотрим немного далее.

### 4. Одна запись затёрла другую

Проблема самая понятная - две транзакции читают одно и то же значение. Обе на его основе считают новое значение. Потом обе записывают результат. В итоге запись одной транзакции затирает результат другой.

Начальное состояние:

```text
Niko = 1500
```

Первая транзакция:

```text
прочитала 1500
посчитала 1500 - 300 = 1200
```

Вторая транзакция:

```text
прочитала 1500
посчитала 1500 - 500 = 1000
```

Дальше:

```text
первая транзакция записала 1200
вторая транзакция записала 1000
```

Итог:

```text
Niko = 1000
```

Но правильный итог должен быть:

```text
Niko = 700
```

У этого есть термин: **lost update**, или **потерянное обновление**.

Это особенно часто возникает, когда разработчик делает логику так:

```sql
1. SELECT balance
2. посчитать новое значение в коде приложения
3. UPDATE balance = новое_значение
```

То есть ошибка не в самой базе, а в том, что приложение забрало данные из базы, посчитало что-то у себя в коде и потом записало старый расчёт обратно.

**Практический совет**: по возможности не делайте запросы по схеме `SELECT -> посчитал в коде -> UPDATE`, если несколько транзакций могут менять эти же данные.

Плохой вариант:

```sql
SELECT balance
FROM accounts
WHERE id = 1;

-- в коде приложения:
-- new_balance = balance - 300

UPDATE accounts
SET balance = 1200
WHERE id = 1;
```

Лучше выполнять изменение атомарно прямо в PostgreSQL:

```sql
UPDATE accounts
SET balance = balance - 300
WHERE id = 1
  AND balance >= 300;
```

В этом случае база сама берёт текущее значение `balance` и изменяет его. Если другая транзакция уже меняет эту же строку, PostgreSQL не даст двум обновлениям тупо затереть друг друга: одна операция будет ждать другую и применится уже к актуальному значению. 

Но иногда всю логику нельзя засунуть в один `UPDATE` и тогда нужно использовать `SELECT ... FOR UPDATE`. `FOR UPDATE` говорит PostgreSQL:

```
я собираюсь менять эту строку;
заблокируй её, чтобы другая транзакция не изменила её параллельно
до завершения моей транзакции
```
Т.е. мы блокируем строку и другие транзакции просто висят и ожидают завершения нашей транзакции.

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = 1
FOR UPDATE;

-- здесь приложение принимает решение,
-- но строка уже заблокирована от конкурентного изменения

UPDATE accounts
SET balance = balance - 300
WHERE id = 1;

COMMIT;
```


Главная мысль:

> Если у тебя схема `SELECT -> бизнес-логика в коде -> UPDATE`, и эту же строку могут менять параллельно, используй `SELECT ... FOR UPDATE` или используй одним атомарным `UPDATE` прямо в PostgreSQL с проверкой условий


### 5. Каждая транзакция по отдельности права, но вместе они ломают все

Это самая мерзкая проблема, потому что она не выглядит очевидно.

Например, рассмотрим такой случай -- есть правило:

```text
в больнице всегда должен быть хотя бы один дежурный врач
```

Таблица:

```text
doctors

id | name | on_call
---|------|--------
1  | Ivan | true
2  | Petr | true
```

Первая транзакция хочет снять Ивана с дежурства.

Вторая транзакция хочет снять Петра с дежурства.

Первая транзакция проверяет:

```sql
SELECT COUNT(*)
FROM doctors
WHERE on_call = true;
```

Получает результатом:

```text
2 дежурных врача
```

Значит можно снимать одного врача.

Вторая транзакция одновременно делает такую же проверку.

Тоже получает в результате:

```text
2 дежурных врача
```

Значит можно снимать одного врача.

Дальше первая транзакция делает:

```sql
UPDATE doctors
SET on_call = false
WHERE id = 1;
```

Вторая транзакция делает:

```sql
UPDATE doctors
SET on_call = false
WHERE id = 2;
```

Обе коммитятся.

Итог:

```text
doctors

id | name | on_call
---|------|--------
1  | Ivan | false
2  | Petr | false
```

Дежурных врачей осталось ноль.

Каждая транзакция по отдельности рассуждала нормально. Но вместе они сломали бизнес-правило.

У этого есть термин: **write skew** или **перекос записи**.

**Практический совет**: если бизнес-правило зависит не от одной строки, а от набора строк, обычного `UPDATE` одной строки может быть недостаточно.

Такие проверки нельзя бездумно делать по схеме:

```
SELECT COUNT(*)
FROM doctors
WHERE on_call = true;

-- потом в коде решили, что всё нормально

UPDATE doctors
SET on_call = false
WHERE id = ...;
```

Если правило критичное, нужно защищать не только конкретную строку, а само бизнес-условие.

В PostgreSQL для этого обычно используют один из вариантов:

```
1. SERIALIZABLE — самый простой концептуально вариант:
   если две транзакции вместе ломают корректность,
   PostgreSQL откатит одну из них с ошибкой,
   а приложение должно повторить транзакцию.

2. Явные блокировки — если мы хотим руками запретить
   параллельное выполнение опасного участка.

3. Ограничения на уровне типов полей базы, типо unique поставить на поле и тогда что не делай у нас всегда будет уникальное поле.
```

Главная мысль:

> Если решение принимается на основе набора строк, а потом меняется только одна строка, подумай про `SERIALIZABLE`, блокировку или ограничение на уровне базы. Иначе две правильные по отдельности транзакции могут вместе сломать бизнес-правило.

## Что PostgreSQL делает, чтобы база правильно поддерживалась?* 

*МОЖЕМ ПРОПУСТИТЬ ЭТОТ РАЗДЕЛ ЕСЛИ ХОТИТЕ.*

PostgreSQL использует механизм MVCC.

MVCC расшифровывается как Multi-Version Concurrency Control.

По-человечески:

> PostgreSQL может хранить несколько версий одной и той же строки и решать, какую версию показывать конкретной транзакции. Т.е. помимо всех основных данных в таблице хранится еще 'журнальчик' с изменениями последних транзакций
 
Например, есть строка:

```text
id = 1, name = Niko, balance = 1500
```

Транзакция делает:

```sql
UPDATE accounts
SET balance = 1200
WHERE id = 1;
```

Очень упрощённо это можно представить так:

```text
старая версия строки:

id = 1, name = Niko, balance = 1500

новая версия строки:

id = 1, name = Niko, balance = 1200
```

PostgreSQL не обязан сразу уничтожать старую версию строки, потому что она может быть ещё нужна другим транзакциям.

Например, одна транзакция началась раньше и по своим правилам видимости ещё должна видеть старый баланс `1500`.

А другая транзакция, которая началась позже, уже может видеть новый баланс `1200`.

То есть важная мысль:

> в PostgreSQL разные транзакции могут одновременно видеть разные версии одной и той же логической строки.

Т.е. PostgreSQL не показыает только закомиченные изменения другим транзакциям, в зависимости от уровня изоляции транзакции она может видеть либо только закомиченные изменения либо уже измененные.

Но MVCC не решает вообще все проблемы автоматически. Он решает часть проблем, а для остальных нужны уровни изоляции, блокировки, ограничения и правильный код приложения.

## Что такое snapshot и зачем он нужен?*

*МОЖЕМ ПРОПУСТИТЬ ЭТОТ РАЗДЕЛ ЕСЛИ ХОТИТЕ.*

Snapshot нужен для ответа на главный вопрос:

> какую версию строки должна увидеть конкретная транзакция?

Если в базе есть несколько версий строки, PostgreSQL должен выбрать одну из них.

Например:

```text
версия 1:
Niko = 1500

версия 2:
Niko = 1200

версия 3:
Niko = 1000
```

Когда транзакция делает:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

PostgreSQL должен понять:

```text
какую версию показать этой транзакции?
1500?
1200?
1000?
```

Вот для этого и нужен snapshot.

Snapshot — это не физическая копия всей базы данных и PostgreSQL не делает копию всех таблиц при каждом `BEGIN`, ведь это было бы слишком дорого . Т.е. Snapshot это набор правил видимости для транзакций.

## Уровни изоляции в PostgreSQL

Уровень изоляции отвечает на вопрос:

> насколько сильно моя транзакция изолирована от изменений других транзакций?

В PostgreSQL на практике важнее всего понимать три уровня:

```text
Read Committed
Repeatable Read
Serializable
```

### Read Committed

Это уровень по умолчанию в PostgreSQL.

Главная идея:

> каждый отдельный SQL-запрос видит только те данные, которые были закоммичены до начала этого конкретного SQL-запроса.

Важно:

```text
не до начала всей транзакции,
а до начала конкретного запроса. 
```

Т.е. внутри транзакции мы можем прочитать два раза одно и тоже, но получить разные значения и это будет **non-repeatable read**. И такая проблема ожидаема для данного уровня изоляции **Read Committed**

Пример:

```sql
BEGIN;

SELECT balance FROM accounts WHERE id = 1;
-- увидели 1500

-- в это время другая транзакция поменяла balance на 1000 и сделала COMMIT

SELECT balance FROM accounts WHERE id = 1;
-- можем увидеть уже 1000

COMMIT;
```

### Repeatable Read

Главная идея:

> транзакция видит snapshot базы на момент старта транзакции, т.е. будут получены все значения котрые были при старте выполнения транзакции.

Если транзакция два раза прочитала одну и ту же строку, она увидит одно и то же значение, даже если другая транзакция уже изменила эту строку и сделала `COMMIT`.

Пример:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT balance FROM accounts WHERE id = 1;
-- увидели 1500

-- другая транзакция поменяла balance на 1000 и сделала COMMIT

SELECT balance FROM accounts WHERE id = 1;
-- всё ещё видим 1500

COMMIT;
```

То есть мир для транзакции как будто заморозился на момент её старта.

### Serializable

`Serializable` — самый строгий уровень изоляции транзакций.

Главная идея простая:

> итог работы параллельных транзакций должен быть таким, как будто они выполнялись не параллельно, а строго по очереди.

То есть PostgreSQL пытается сохранить для нас такую картину мира:

```
сначала полностью выполнилась транзакция T1,
потом полностью выполнилась транзакция T2
```

или наоборот:

```
сначала полностью выполнилась транзакция T2,
потом полностью выполнилась транзакция T1
```

Главное, чтобы итог можно было объяснить каким-то последовательным порядком.

Важно: PostgreSQL не ставит все транзакции в одну очередь. Он выполняет их параллельно. Но если движок PostgreSQL высчитывает, что параллельное выполнение даёт результат, который нельзя получить последовательными запросами, он откатывает одну из транзакций.

**Пример**:

Допустим, у нас есть правило:

```
у одного пользователя может быть только один активный заказ
```

Таблица пустая:

```
orders

id | user_id | status

```


Одновременно приходят два HTTP-запроса:

```
Запрос 1: создать активный заказ для user_id = 10
Запрос 2: создать активный заказ для user_id = 10
```

Первая транзакция проверяет:

```
SELECT COUNT(*)
FROM orders
WHERE user_id = 10
  AND status = 'active';
```

Получает:

```
0 активных заказов
```

Вторая транзакция одновременно делает такую же проверку:

```
SELECT COUNT(*)
FROM orders
WHERE user_id = 10
  AND status = 'active';
```

Тоже получает:

```
0 активных заказов
```

Дальше первая транзакция делает:

```sql
INSERT INTO orders(user_id, status)
VALUES (10, 'active');
```

Вторая транзакция делает:

```sql
INSERT INTO orders(user_id, status)
VALUES (10, 'active');
```

Если обе транзакции спокойно закоммитятся, получится:

```
orders

id | user_id | status
---|---------|--------
1  | 10      | active
2  | 10      | active
```

Бизнес-правило сломано: у пользователя стало два активных заказа.

Если обе транзакции запустить на уровне `SERIALIZABLE`, PostgreSQL будет следить за такой ситуацией.

Первая транзакция:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT COUNT(*)
FROM orders
WHERE user_id = 10
  AND status = 'active';

INSERT INTO orders(user_id, status)
VALUES (10, 'active');

COMMIT;
```

Вторая транзакция одновременно:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

SELECT COUNT(*)
FROM orders
WHERE user_id = 10
  AND status = 'active';

INSERT INTO orders(user_id, status)
VALUES (10, 'active');

COMMIT;
```

На `Serializable` нормальный результат может быть таким:

```
первая транзакция успешно закоммитилась;
вторая транзакция получила ошибку сериализации.
```

Например:

```
ERROR: could not serialize access due to read/write dependencies among transactions
```

Можно также указать уровень изоляции отдельно:

```sql
BEGIN;

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- SQL-команды транзакции

COMMIT;
```

В реальном приложении это часто задаётся не руками в SQL, а через драйвер или ORM.
Смысл при выставлении такого уровня изоляции транзакции такой: 
```
эту транзакцию нужно выполнить так, что
её результат должен быть совместим с последовательным выполнением.
```

**Какая ответственность лежит на разработчики, а какая на PostgreSQL?**

PostgreSQL отвечает за то, чтобы не пропустить паралелльное выполнение транзакций, которое даст результат не такой как при последовательном выполнении.

Разработчик отвечает за то, чтобы:

```
1. включить SERIALIZABLE там, где это реально нужно;

2. написать транзакцию так, чтобы она была правильной;

3. обработать ошибку сериализации;

4. повторить транзакцию заново при неудачи
```

**Самый важный пункт** — повтор транзакции.

Если PostgreSQL откатил транзакцию с ошибкой сериализации, нельзя просто показать пользователю “всё сломалось” во всех случаях. Часто правильное поведение приложения — повторить транзакцию.

**Практические рекомендации**

Не нужно включать `Serializable` вообще везде. Это самый строгий уровень изоляции, и под нагрузкой он может чаще приводить к откатам транзакций и увеличении нагрузки на базу данных.

Обычно логика такая:

```
простая операция над одной строкой:
  часто достаточно атомарного UPDATE

нужно прочитать строку, потом изменить эту же строку:
  часто помогает SELECT ... FOR UPDATE

нужно стабильно читать данные внутри транзакции:
  можно использовать REPEATABLE READ

есть сложное бизнес-правило по набору строк:
  нужно подумать про SERIALIZABLE, явные блокировки или ограничения БД
```

**Коротко**:

> Serializable — это режим “если параллельные транзакции вместе могут наделать херни, PostgreSQL не даст всем им успешно закоммититься”. Но приложение должно быть готово повторить завершенную с ошибкой транзакцию.

## Что вы должен вынести из урока?

Главная мысль урока:

> Код, который правильно работает при одном запросе, может начать ломать данные, когда несколько запросов одновременно работают с одними и теми же данными.

Поэтому при работе с базой данных разработчик должен думать не только о том, что делает его SQL-запрос сам по себе, но и о том, что в этот же момент могут делать другие транзакции.

**==Нужно запомнить следующее:==**

1. **Не делайте бездумно схему `SELECT -> посчитал в коде -> UPDATE`.**

Если несколько транзакций могут менять эти же данные, то между `SELECT` и `UPDATE` значение в базе уже может измениться. Лучше, если возможно, делать изменение одной SQL-командой:

2. **Проверки лучше зашивать прямо в SQL-команду.**

Так проверка и изменение происходят вместе одной командой, а не разрываются между базой и кодом приложения.

3. **Если нужно сначала прочитать строку, потом принять решение и изменить её — используйте `SELECT ... FOR UPDATE`.**

`FOR UPDATE` нужен, чтобы другая транзакция не изменила эту же строку, пока текущая транзакция не завершилась.


4. **Если внутри транзакции нужны неизменяемые в момент транзакции данные — используйте `REPEATABLE READ`.**

На уровне `READ COMMITTED` два одинаковых `SELECT` внутри одной транзакции могут вернуть разные данные, потому что между ними другая транзакция могла сделать `COMMIT`.

Если такое поведение опасно, можно использовать `BEGIN ISOLATION LEVEL REPEATABLE READ;`

5. **Лучше используй ограничения в базе данных, чем обрабатывай их кодом**

6. **`SERIALIZABLE` —  режим гарантирующий результат транзакций как при последовательном выполнении, но с возможными откатами.**

Если используете `SERIALIZABLE`, приложение должно уметь повторять транзакцию. Во вторых не используйте `SERIALIZABLE` везде бездумно, а только в конкурентных участках.

Сначала нужно подумать:

```text
можно ли решить задачу атомарным UPDATE?
можно ли добавить условие в WHERE?
можно ли использовать SELECT ... FOR UPDATE?
можно ли выразить правило через constraint или unique index?
нужен ли здесь REPEATABLE READ?
нужен ли здесь SERIALIZABLE?
```

Чем проще решение на уровне базы, тем лучше.

**Коротко**:
 
> Задача разработчика — писать SQL и транзакции так, чтобы параллельное выполнение не превращало данные в неправильное говно.
